## 2026-11-02 목적: 대형마트에서 가격표가 적당한지 판단
- 결정: 주된 용도는 대형마트 안에서 가격표의 값이 적당한지 판단하는 것이다. 페이지는 품목별 KAMIS 오늘 평균 단위 가격과 "요즘 평년보다 18% 비싼 시기" 같은 한 줄을 보여 주고, 비교는 사람이 눈으로 한다.
  - 집에서 목록을 체크해 두고, 마트에서는 그 목록을 보며 가격표와 비교한다.
  - 단위 가격은 대형마트 가격표에 적힌 단위(100g당, 1개당 등)에 맞춰 보여 준다.
- 이유: 장보기 전에 결정하고 싶은 것 가운데 사용자가 "가게에서 비교"를 가장 중요하게 골랐고, 주로 대형마트에서 장을 본다. 대형마트 가격표에는 보통 단위 가격이 있어서, 같은 단위로 보여 주면 바로 비교할 수 있다. 평균과 비교하면 "이 가게가 비싼지", 평년과 비교하면 "요즘 원래 비싼 시기인지"를 알 수 있다.
- 버린 대안: 예산 잡기나 살지 말지 판단을 주된 용도로 두기. KAMIS 평균만 보여 주기. 가격표 값을 입력하면 "평균보다 10% 비쌈"처럼 판정하기(마트 안에서 한 손으로 숫자를 쳐야 해서 1차에서 뺌).
- 참고: 목록을 집에서 체크하는 흐름과 단위를 가격표에 맞추는 것은 Claude가 짐작해 정리에 넣었고, 사용자가 맞다고 했다.

## 2026-11-02 설계 ⑤ 오프라인·목록 저장 (2026-11-03 목록 대신 즐겨찾기를 저장)
- 결정

  - 목록은 폰 안 브라우저 저장 공간(localStorage)에 품종 코드와 개수만 저장한다. 가격은 늘 최신 `prices.json`에서 가져온다.
  - 저장을 맡는 코드는 한 파일로 떼어 두고, 화면은 그 파일의 함수(목록 읽기, 담기, 빼기, 개수 바꾸기)만 부른다. 함수는 처음부터 결과를 나중에 돌려주는 방식(Promise)으로 만든다.
  - 처음 열었을 때 맨 위에 한 번 "홈 화면에 추가하면 앱처럼 쓰고, 인터넷 없이도 열려요" 안내를 띄운다. 닫으면 다시 나오지 않는다.

- 이유: 인터넷 저장(가족 공유)은 응답을 기다려야 하므로, 처음부터 Promise 방식이면 공유로 바꿀 때 화면 코드를 고치지 않아도 된다. 아이폰은 홈 화면 추가를 공유 메뉴에서 직접 해야 해서 안내가 없으면 모르고 지나치기 쉽다. 처음 쓰는 가족이 무엇을 할지 바로 알게 한다.
- 버린 대안: 저장 함수를 지금은 바로 끝나는 방식으로 만들고 공유할 때 화면 코드도 고치기. 홈 화면 추가 안내 없이 두기. 빈 목록을 빈 화면 그대로 두기.
- 참고: 아이폰 사파리는 웹사이트를 7일 동안 열지 않으면 그 사이트가 저장한 내용을 지울 수 있다고 알려져 있고, 홈 화면에 추가한 앱은 이 규칙에서 빠진다. 홈 화면 추가 안내는 목록을 지키는 데도 도움이 된다.

## 2026-11-03 품종 목록을 다시 만들 때 철이 지난 품종은 남기기
- 결정: 품종 목록을 다시 만들 때, 그날 전체 평균 응답에 있는 품종은 새 것(조사 단위·이름·등급)으로 바꾸고, 응답에 없는 품종은 기존 것을 남긴다. 첫 "품종 목록도 다시 만들기"에서 사라진 철 지난 품종 46개도 되살렸다(목록 159개).
- 이유: 전체 평균 응답에는 그날 조사한 품종만 온다. 응답만으로 목록을 새로 쓰면 철이 지난 품종이 사라져, 철이 돌아와도 목록을 손으로 다시 만들기 전까지 수집되지 않는다. "KAMIS 소매 품목 전부"로 정한 범위(2026-11-02)를 지키려는 것이다.
- 버린 대안: 그날 응답만으로 목록을 새로 쓰기(첫 실행에서 실제로 46개가 사라졌다).
- 참고: Claude가 정해 구현했고 보고에서 알린다. 철이 지난 품종의 조사 단위는 예전 코드표 값이라, 철이 돌아왔을 때 KAMIS 단위와 다르면 수집 요약에 "단위가 다른 품종"으로 나온다. 그때 "품종 목록도 다시 만들기"로 다시 돌리면 고쳐진다.

## 2026-11-03 검색창을 누르면 부류별로 훑어보기 (같은 날 첫 화면의 "전체 품목"으로 늘 보이게 바뀜)
- 결정: 아무것도 치지 않은 채로 검색창을 누르면 지금 값이 있는 품종 전부를 부류별로 보인다(채소류 → 과일류 → 수산물 → 식량작물 → 특용작물, 부류 안은 가나다순). 맨 위 부류 칸을 누르면 그 부류로 건너뛴다. 담기와 합계는 검색과 같고, ✕는 내 목록으로 돌아간다.
- 이유: 품종이 늘어(목록 159개, 값 있는 품종 113개) "부세수입", "흰다리"처럼 이름을 모르면 찾기 어려운 품종이 생겼다. 가족이 설명 없이 쓰려면 이름을 몰라도 훑어 고를 수 있어야 한다. 사용자가 시안을 보고 그대로 진행하자고 했다.
- 버린 대안: 지금처럼 검색만 두기.
- 참고: 부류 순서와 부류 안 가나다순은 Claude가 제안하고 사용자가 받아들였다. 시안은 칸 줄을 여러 줄로 접었지만, 폭 320px에서 세 줄(158px)이 되어 목록 자리가 좁아져 한 줄로 두고 옆으로 밀게 바꿨다(Claude가 구현 중에 정함).

## 2026-11-03 화면의 중심을 "시세 찾아보기 + 즐겨찾기"로 (장보기 목록·예상 총액 뺌)
- 결정: 장보기 목록 담기, 개수(−/+), 예상 총액을 화면에서 뺀다. 품목을 찾아 시세를 자세히 보는 것이 중심이고, 자주 보는 품종은 상세 화면의 ☆로 즐겨찾기에 넣어 첫 화면 맨 위에서 한눈에 본다. 즐겨찾기는 폰마다 따로다. 즐겨찾기는 상세 화면에서만 넣고 뺀다. 폰에 이미 담아 둔 목록은 처음 열 때 즐겨찾기로 옮기고 개수는 버린다. 목적(마트에서 가격표가 적당한지 판단)과 1차 성공 기준은 그대로이고, 목적 기록의 "집에서 목록을 체크해 두고 그 목록을 보며 비교"는 "즐겨찾기를 보거나 검색해 비교"로 바뀐다.
- 이유: 사용자가 원한 것은 예상 영수증이 아니었다. 과자, 라면, 고기가 KAMIS 소매 품종에 없어서 실제 장바구니 총액을 낼 수 없고, 담기와 합계가 화면 중심처럼 보여 정작 시세 찾기가 묻혔다. 즐겨찾기를 상세에서만 넣는 것은 줄에 이미 이름·그래프·가격·%가 있어 ☆까지 넣으면 폰 폭에서 빡빡하고 잘못 누르기 쉬워서다(Claude 의견, 사용자가 골랐다).
- 버린 대안: 영수증을 고쳐 계속 쓰기. 즐겨찾기 ☆를 검색 결과·전체 품목 줄 끝마다 두기.
- 참고: 수집 쪽은 바꾸지 않는다. 조사 단위 기준 범위(`range`)는 총액에 쓰던 값이라 화면이 쓰지 않게 되지만 파일에는 남는다.

- 참고: 검색 결과를 묶지 않는 것과 ←가 보던 자리로 돌아가는 것은 Claude가 설계 정리에 넣었고 사용자가 받아들였다.

## 2026-11-03 생김새: 증권 앱 관심 종목처럼, 내림은 빨강·오름은 파랑

- 참고: 2026-11-03 "영수증 글꼴 파일과 글꼴 도구를 지운다"로 글꼴 만들기 도구가 없으므로 숫자 글꼴용 도구를 새로 둔다. Geist 원본은 내려받기 전에 허락을 받는다.

- 이유: 처음 요청에 계란·돼지고기·닭고기가 있었는데 1차에서 빠져 있었다. 2026-11-03에는 문서의 예시 키로 부른 축산물이 빈 답이었지만, 2026-11-04 날짜를 넣어 부르니 29줄이 1주·1개월·1년 전, 평년 값과 함께 왔다. 마트 소고기 가격표에는 늘 등급이 적혀 있어 등급마다 줄이 있어야 견줄 수 있다. 사용자가 Claude 제안대로 정했다.
- 버린 대안: 이마트 고기 값(참가격)만 보기(이마트 고기와 계란 일부는 지점 1~2곳만 조사한다).
- 참고: 문서의 예시 키로 확인한 것. 가게별 기간 API(`periodRetailProductList`)는 축산물에 가게 줄 없이 "평균·평년·전국" 줄만 주고, 한우는 등급 번호를 바꿔도 늘 1++ 값을 준다. 품목별 기간 API(`periodProductList`)는 등급을 가린다. 두 기간 API의 날짜는 부류별 API보다 하루 앞선다(부류별 11-03 당일 값 = 기간 API 11-02 값, 다섯 품종에서 날마다 같았다). 축산물은 주말에도 값이 있다. 한우·돼지 등의 품종 번호는 등급과 상관없이 같아서(등심 1++·1+·1등급 모두 22) 품종 id에 등급 번호를 붙여야 한다.

## 2026-11-04 축산물·지난 값 채우기 구현: Claude가 정한 세부 여섯 가지 (같은 날 품목별 기간 API, 날짜 하루 밀기, 등급 번호 대응표는 빠짐)
- 결정
  - 빈 1개월 전·1년 전 값은 부류 안에서 당일 값이 있는 품종의 칸이 모두 비었을 때만 다시 불러 채운다. 몇 품종만 비었으면 그날 조사는 있었고 그 품종만 값이 없던 것이라 다시 부르지 않는다.
  - 축산물의 30일 추이는 품목별 기간 API(`periodProductList`)로 받고, 그 날짜를 하루 뒤로 밀어 부류별 API의 날짜에 맞춘다.
  - 품목별 기간 API는 축산물 등급 번호를 따로 쓰므로 바꿔 부른다: 한우 01~03은 그대로, "00"(돼지·닭·우유)과 "71"(계란)은 "01", 수입 소고기 "81"(미국산)·"82"(호주산)은 "01"·"02".
  - 축산물 품목 이름은 장볼 때 쓰는 말로 바꾼다: 소 → 한우, 돼지 → 돼지고기, 닭 → 닭고기, 육계(kg) → 육계. 등급("1+등급")과 산지("미국산")는 품종 이름 뒤에 붙인다.
  - 기준일을 정할 때 축산물 줄은 보지 않는다.
  - "소고기"·"쇠고기"로 찾으면 한우도 나온다.
- 이유: Claude가 구현하며 정했고, 사용자가 보고를 보고 받아들였다. 채우기 조건은 KAMIS가 주말·공휴일이면 칸을 통째로 비우기 때문이고, 몇 품종만 빈 날 다시 부르면 같은 값이 와서 부르는 횟수만 는다. 날짜 밀기는 문서의 예시 키로 28줄 모두 기간 API의 11-02 값이 부류별 API의 11-03 당일 값과 같았기 때문이며, 밀지 않으면 그래프 끝 점과 큰 가격이 어긋난다. 등급 번호는 부류별 API의 번호로 부르면 "데이터 없음"이 와서 28줄을 하나씩 맞춰 찾았다. "소"는 1++~1등급이고 값이 한우 수준이라 한우로 봤다(KAMIS 문서에서 확인하지는 못했다). 축산물은 농수산물보다 값이 먼저 올라와서, 보면 농수산물 값이 빈 날이 기준일이 될 수 있다.
- 버린 대안: 칸이 하나라도 비면 다시 부르기. 가게별 기간 API로 축산물 추이 받기(한우 등급을 가리지 않는다). 기간 API 날짜를 그대로 쓰기. KAMIS 이름("소", "돼지", "닭") 그대로 쓰기.
- 참고: 품종 목록의 축산물 29줄은 문서의 예시 키로 받은 11-04 응답으로 만들었다(다음 "품종 목록도 다시 만들기"에서 같은 줄로 다시 만들어진다).

## 2026-11-04 축산물 30일 값은 부류별 API를 날마다 불러 받는다
- 결정
  - 축산물의 30일 그래프는 부류별 API(`dailyPriceByCategoryList`, 부류 500)를 기준일부터 거꾸로 30일 동안 하루에 한 번씩 불러, 그날의 당일 값으로 그린다. 한 번 부르면 축산물 모든 줄이 오고, 기준일 것은 이미 받은 값을 쓴다. 받기에 실패한 날은 그래프에서 그날만 빠진다.
  - 품목별 기간 API(`periodProductList`), 날짜 하루 밀기, 등급 번호 대응표를 지운다.
  - 수집 기록의 한 줄 요약 아래에 축산물만 따로 센 줄을 더하고, 값이 없어 빠진 축산물은 이름을 적는다(예: "축산물 새 항목 28개, 값이 없어 빠진 품종 1개(닭고기 절단육)"). 실행을 실패로 끝내지는 않는다.
- 이유: 검토에서 두 문제가 나왔다. 기간 API용 등급 번호를 손으로 적은 표에 없는 번호가 오면 그 품종이 메일 없이 날마다 빠진다. 큰 가격(기간 API 값)과 평년 %(부류별 API 값)가 하루 어긋남을 상수로 맞춰 둔 탓에 서로 다른 날 값이 될 수 있다. 부류별 API 하나로 받으면 큰 가격, 그래프, 평년 %가 모두 같은 날짜 값이 되고 등급 번호도 그대로 쓴다. 부르는 횟수는 29번으로 전과 거의 같다(문서의 예시 키로 30번 부르는 데 21초, 주말과 한글날도 28줄 모두 값이 있었다). 축산물은 철이 없어 빠진 품종이 생기면 이상한 것이라 이름을 따로 남긴다. 실패로 끝내면 그날 농수산물 갱신까지 막힌다. Claude가 제안했고 사용자가 "이대로 고치자"고 했다.
- 버린 대안: 등급 번호 표를 품종 목록 만들 때 순번으로 계산해 두기, 기간 API를 두고 큰 가격만 부류별 당일 값으로 바꾸고 어긋나면 경고하기(둘 다 서로 다른 API를 섞어 쓰는 원인이 남는다). 축산물이 빠지면 실행을 실패로 끝내기.
- 참고: 키 없이 도는 샘플 모드에서는 샘플 응답이 날짜를 가리지 않아 축산물 그래프가 하루치뿐이다.

## 2026-11-10 전체 검토에서 나온 것 가운데 정할 것이 없는 세 가지를 먼저 고친다
